## Notebook offline delete/edit rounds

Both rounds used only the fixed disposable notebook. The LAN replication proxy
was stopped; native Notes Binder deletion on Palma and rename on Lumi ran with
both devices disconnected. Server revision stayed unchanged. Native replication
was then restarted one device at a time, with the first branch's server state
verified before reconnecting the second device.

| Round | First reconnect | Server and both native providers after conflict |
| --- | --- | --- |
| First | Lumi edit | Enabled (`status=1`), Lumi edited title retained; Palma deletion lost |
| Second | Palma deletion | Removed (`status=0`), Lumi edited title absent; deletion won |

Protocol trace proves two sibling proposals from the same parent in **each**
round, plus a 409 conflict response. Round one siblings are generation 73 from
generation 72. Round two has its own siblings and parent; these are not replayed
identical branches. Consequently opposite outcomes do not prove reconnect order
caused a different winner. They qualify actual notebook delete/edit convergence
and demonstrate that neither delete-wins nor edit-wins is an unconditional rule.
Native provider application, not editor-openability of a removed note, is the
application evidence here. No custom server conflict policy was introduced.

A 409 can reject a sibling at `proposeChanges`, before its full body is uploaded.
Future server history must distinguish complete bodies actually received from
proposal-only revision identities. Keeping a changes feed cannot guarantee every
losing edit is preserved; the proposed server-only archive remains optional.
