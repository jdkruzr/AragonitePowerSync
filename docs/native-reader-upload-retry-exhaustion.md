# Native Reader upload retry exhaustion

2026-10-08. Owned clean-v2 PDF only; fresh verified native sessions, Reader enabled and Notes disabled. Evidence: `artifacts/gateway-lab/qualification/reader-native-fresh-upload-fault/`.

Palma saved Z after the previously stranded Y. Four new native objects (two shape ZIPs, two pressure files) each received nine real PUT attempts, all injected HTTP 503 before backend storage. The 36 attempts occupied roughly six seconds, ending in native Upload Error. The scoped fault lasted about 65 seconds. Removing it produced no successful upload during the following 120 seconds without helper actions, manual Sync, source reopen, login renewal or host publication. This is actual asset retry exhaustion, separate from the previously qualified Couchbase disconnect recovery.

Separate bounded recovery controls also produced no successful asset PUT: source reopen/native UI Sync (90 seconds), ordinary-UID Binder 3 requeue of the identical current UserDataBean (90 seconds), timestamp-only mode-7 save (60 seconds), and targeted Binder 14 stop followed by Binder 17 start for this book (60 seconds). These are assisted controls, not passive automatic recovery. An initial timestamp guard rejected integer versus Double strokeWidth before publication; the accepted retry preserved numeric 4.0 and changed only updatedAt.

After the timestamp plus targeted job control, server mode-7 commitId, commitInfo and updatedAt advanced. The reader commit received a new revision with an identical body. All four rejected resource objects remained absent. Their combination was not independently isolated. Metadata receipt, resource storage, commit publication and native application must therefore remain separate acknowledgements; a sync-success status or fresh commit revision is insufficient evidence of complete ink delivery.

Before any host recovery, Palma retained 17 native shape records and 11 pressure files; the 10.3 II remained at 13 and nine. Across requeue, timestamp and job controls, every field of all 17 source records and all 11 pressure payloads stayed exact. Earlier native ink semantics and unrelated Reader/library guards passed. The only notebook exception is the previously confirmed user-created Palma Notebook-1; no baseline reset or deletion was used.

Static path builders led to `/sdcard/.ksync/document/<owned-book>/shape` and `/sdcard/.ksync/point/<owned-book>`. All four rejected upload bodies remain there. Each was escrowed read-only and verified against its actual rejected PUT size and SHA256. No geometry or pressure was synthesized. This proves exact native resource retention, not unprivileged app access to every cache path.

A separately journaled host-assisted recovery stores these exact bodies through the existing scoped OSS facade, then publishes an unchanged-body reader commit revision followed by the existing type-6 MESSAGE with fresh syncAt. Two preliminary host requests were rejected before storage because the privacy-filtered request journal replaces the book ID with `<redacted>`; the corrected request restores only the fixed owned fixture ID. Recovery outcome and native verification are recorded below when complete.

Server design consequence: promptly persist and acknowledge asset PUTs durably, detect incomplete resource closure separately from metadata, and retain a recovery workflow after finite native upload retries. Couchbase replication retries cannot be assumed to repair exhausted OSS work. Nine observed attempts per object do not establish the exact composition of SDK and outer retry layers. A fresh physical-edit resubmission and purely native recovery remain unqualified.

Assisted recovery result: all four exact native bodies were durably accepted with HTTP 200. During the 90-second notification window, the receiver acquired all 11 pressure files but remained at 13 native shapes. Reader logs report needPull=false: cloud userDataUpdateDate is older than lastMetadataPullTime. A separately invoked guarded full native pull then applies the four missing Y/Z records. Both devices have the same 17 shape IDs and 11 exact pressure files. Every new receiver record matches source semantics; all prior receiver records match its own baseline. One older source/peer information-revision difference predates this experiment and is preserved. Full replay leaves the receiver unchanged. Final screenshots show Z; source semantics/pressure remain exact and unrelated-library guards pass.

This is host-assisted resource publication plus an explicit native full-pull override, not autonomous recovery. Server notification fixes asset availability but cannot be assumed to overcome Reader's timestamp gate after an incomplete earlier pull. Durable closure and a supported reconciliation/import trigger belong in the facade design.

Validation: signature-matched in-place helper installations; assembleDebug/lintDebug passed for both recovery additions. Scoped OSS selector and Reader scope tests previously passed (12 OSS, eight Reader scope); live exercise validates 36 rejected native PUTs and four exact successful assisted PUTs. Snapshots retain tested APK, source, build logs and drivers. SHA256SUMS is verified after sealing.

Static freshness gate: shipped Go Reader CheckPullPointRequest selects the cloud SyncMetadataModel with greatest updatedAt, computes docDataUpdateTime from its extraAttributes/lastAccess, and sets needPull only when that value is strictly greater than KReaderLocalSyncProvider.loadLastMetadataPullTime. This corroborates the runtime skip; it is not a claim that mode-7 updatedAt or commit revision alone changes the metadata-derived ink timestamp.
